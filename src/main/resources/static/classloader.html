⚙️ JVM Subsystem

JavaClass Loader

The gatekeeper of the JVM — it finds, loads, links, and initializes every class before a single line of your code runs.

Class Loader Hierarchy

Class loaders follow a strict parent-delegation model. Before loading a class, each loader asks its parent first. Only if the parent can't find it does the child try.

Built into JVM

Bootstrap Class Loader

Loads core Java classes: java.lang.*, java.util.*, java.io.* etc. from rt.jar. Written in native C — not a Java class itself.

Extension

Platform Class Loader

Loads Java SE platform APIs and extension libraries from $JAVA_HOME/lib/ext. Called "Extension Loader" in Java 8 and below.

Application

Application Class Loader

Loads your application classes from the classpath (-classpath or CLASSPATH env). This is the default loader for user-defined classes.

Custom

Custom Class Loader

You can write your own by extending ClassLoader. Used by web servers (Tomcat), OSGi, hot-reload frameworks, and bytecode manipulation tools.

Key Properties
Delegation

Parent-First Delegation

Every class loader delegates to its parent before trying itself. This prevents malicious code from replacing core classes like java.lang.String.

Uniqueness

Class Identity = Loader + Name

Two classes with the same name loaded by different loaders are different classes to the JVM. This enables web server isolation per webapp.

Lazy

Lazy Loading

Classes are loaded on demand — only when first referenced. Your entire classpath is NOT loaded at startup, keeping startup times fast.

Visibility

Visibility Rules

A class loaded by a child loader can see classes loaded by its parent. But a parent loader cannot see classes loaded by its children.

Hot reload

Dynamic Class Loading

Frameworks like Spring Boot DevTools and JRebel use custom class loaders to reload changed classes without restarting the JVM.

Security

Bytecode Verification

Before a class runs, the JVM verifier checks: valid instruction opcodes, consistent stack depths, type safety, no illegal access — all without running the code.

Common Class Loading Errors

ClassNotFoundException

Class not found anywhere on the classpath. Usually a missing JAR, wrong package name, or typo in Class.forName().

Class.forName("com.missing.Foo") // thrown

NoClassDefFoundError

Class was present at compile time but missing at runtime. More severe — it's an Error not an Exception. Often a classpath config issue in deployment.

// Compiled fine, JAR missing at runtime

ClassCastException

Two loaders loaded the "same" class — they are distinct types to the JVM. Casting between them fails even if the bytecode is identical.

// Foo from loader A ≠ Foo from loader B

ExceptionInInitializerError

An exception was thrown inside a static { } block during class initialization. The class can never be used — subsequent access throws NoClassDefFoundError.

static { throw new RuntimeException(); }
