Key Concepts
🔗

Reference-Based Access

You never touch heap objects directly. Stack variables hold a reference (memory address). The JVM dereferences it to reach the actual object on the heap.

🤝

Shared Across Threads

All threads share the heap. This enables objects to be passed between threads — but also requires synchronization (synchronized, volatile) to be safe.

🆕

Created with new

Every new keyword allocates space on the heap. This includes arrays, class instances, strings created via new, and anonymous classes.

♻️

Garbage Collected

Objects with no live references become eligible for GC. The JVM's GC thread reclaims their space. You can hint with System.gc() but can't force it.

🏊

String Pool

String literals live in a special pool inside the heap. "hello" == "hello" is true because both point to the same pooled object.

📏

Configurable Size

Use -Xms (initial) and -Xmx (max) JVM flags to tune heap size for your application's needs.

Heap Generations (Generational GC)

The heap is split into generations. Most objects die young — the generational hypothesis — so the JVM optimizes GC by collecting the Young Generation frequently and Old Generation rarely.

Young Generation

New objects are born here. Divided into Eden + two Survivor spaces. Minor GC runs frequently and is very fast.

~1/3 of heap
→

Old Generation

Objects that survive multiple Minor GCs get promoted here. Major GC (Full GC) runs here — slower, causes longer pauses.

~2/3 of heap
+

Metaspace

Class metadata, method bytecode, static variables (Java 8+). Replaced PermGen. Uses native memory — not heap.

native memory
How Garbage Collection Works
1

Mark

GC starts from GC Roots (stack refs, static fields) and marks all reachable objects.

2

Sweep

Unreachable (unmarked) objects are identified. Their memory is noted as free.

3

Compact

Live objects are moved together to eliminate fragmentation. Pointers updated.

4

Promote

Survivors of enough Minor GCs get promoted to Old Generation.
